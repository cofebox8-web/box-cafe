# مرجع تدفق الطلب واللحظية — بوكس كافي

> **السؤال المطلوب الإجابة عليه بدقة:** "إذا تم طلب من المنيو، هل يطلع بصفحة المطبخ لحظياً؟ وكذلك الأدمن؟ وهل تتغير الحالة لحظياً؟"
>
> **منهجية هذا المرجع:** قراءة مباشرة للكود الفعلي الحالي على القرص بتاريخ 2026-09-28، مع تحقق حي عبر استدعاءات RPC حقيقية على قاعدة الإنتاج (بمفتاح anon العام فقط، بلا أي بيانات دخول). كل ما هو مؤكد "حياً" مذكور صراحة؛ وما هو مبني على قراءة كود فقط مذكور كذلك.

---

## 0. تصحيح جوهري قبل الإجابة: "الطلب من المنيو" لم يعد موجوداً بالشكل المعروف سابقاً

اكتشفت أثناء التدقيق تغييراً معمارياً جوهرياً حدث للمشروع مؤخراً (ترحيل [`202609270017_waiter_order_mode_and_public_write_lockdown.sql`](../supabase/migrations/202609270017_waiter_order_mode_and_public_write_lockdown.sql)):

- **دالة `place_customer_order` أصبحت ممنوعة تماماً عن الزبون والمجهول:**
  ```sql
  revoke all on function public.place_customer_order(...)
    from public, anon, authenticated;
  ```
  تحققت من هذا **حياً الآن** عبر استدعاء مباشر بمفتاح anon العام:
  ```
  → {"code":"42501","message":"permission denied for function place_customer_order"}
  ```
- ملف `public/js/menu-app.js` نفسه يبدأ بتعليق صريح: *"BOX COFE — Customer Read-Only Menu Controller ... Pure Read-Only"*. تحققت أن الملف (619 سطراً) **لا يحتوي أي كود لسلة شراء أو زر طلب أو تتبع حالة طلب** — تم حذف كل ذلك بالكامل.

**الخلاصة:** الزبون الذي يمسح QR ويفتح `/menu/...` **يتصفح المنيو فقط ولا يقدر يرسل طلباً بنفسه إطلاقاً الآن**. الطلب الفعلي يُنشأ حصراً من طرف **موظف الويتر** عبر صفحة `/waiter` (بعد تسجيل دخوله)، باستخدام دالة جديدة اسمها `place_waiter_order`. تحققت حياً أن المنيو نفسه (`get_customer_menu`) لا يزال قراءة عامة تعمل، وأنه يحتوي فعلاً منتجات حقيقية الآن (لم يعد فارغاً).

**بالتالي، سأجيب على سؤالك بالمعنى الحقيقي الحالي: طلب يُنشئه الويتر — هل يظهر بالمطبخ والأدمن لحظياً، وهل تتغير حالته لحظياً؟**

## 1. مسار الطلب الفعلي الحالي (كما يعمل اليوم بالضبط)

```
موظف الويتر (/waiter، مسجّل دخول بدور roadside)
   → يبني السلة من نفس منيو الفرع (قراءة حية)
   → يضغط "تأكيد وإرسال الطلب للمطبخ"
   → استدعاء RPC: place_waiter_order(...)
       └─ داخلياً يستدعي نفس place_customer_order الأصلية (تحقق الأصناف
          والخيارات، حساب السعر من القاعدة، إدراج معاملاتي واحد)
       └─ يُلصق الطلب: source='roadside', order_mode='car'|'walkin'
   → إدراج صف جديد في جدول public.orders
       └─ الجدول مُدرَج في نشر Supabase Realtime (منذ الترحيل الأساسي
          202609240003_kitchen_display_and_status.sql، لم يُلغَ لاحقاً)
   → أي صفحة مشتركة بقناة Realtime على جدول orders تستلم الحدث فوراً
```

## 2. هل يظهر الطلب بالمطبخ لحظياً؟ ✅ نعم — تحقق من الكود مباشرة

[`public/js/kitchen-app.js:134-152`](../public/js/kitchen-app.js):
```js
function subscribeToKitchenOrders() {
  ...
  kitchenRealtimeChannel = supabase
    .channel(`kitchen-orders-${kdsState.branchSlug}`)
    .on("postgres_changes", { event: "*", schema: "public", table: "orders" }, async (payload) => {
      const isInsert = payload.eventType === "INSERT";
      const ok = await loadKitchenOrders();
      if (ok && isInsert) { playBaristaOrderBell(); showLiveToast("وصل طلب جديد إلى المطبخ."); }
    })
    .subscribe((status) => {
      if (status === "CHANNEL_ERROR" || status === "TIMED_OUT") { ... }
      else if (status === "SUBSCRIBED") { loadKitchenOrders(); } // إعادة جلب عند أي إعادة اتصال صامتة
    });
}
```
- آلية دفع حقيقية (WebSocket عبر `postgres_changes`)، **ليست استطلاعاً دورياً (polling)** — أي طلب جديد (`INSERT`) يصل خلال أقل من ثانية عادةً في الشبكة الطبيعية.
- يقرع جرساً ويظهر إشعاراً مرئياً فقط بعد تأكيد نجاح إعادة الجلب الفعلي (`ok && isInsert`) — لا يوجد إشعار وهمي عند فشل التحميل (تحققت من هذا الجزء في تدقيق سابق منفصل ولا يزال قائماً).
- شبكة أمان إضافية موجودة: إعادة جلب تلقائية عند `SUBSCRIBED` (يغطي إعادة الاتصال الصامتة)، وعند عودة رؤية التبويب (`visibilitychange`, السطر 461)، ومحاولة إعادة واحدة بعد 5 ثوانٍ عند فشل التحميل (`kitchenRetryTimer`).

## 3. هل يظهر الطلب بالأدمن لحظياً؟ ✅ نعم — تحقق من الكود مباشرة

[`public/js/admin-app.js:276-302`](../public/js/admin-app.js):
```js
function subscribeAdminOrders() {
  ...
  .on('postgres_changes', { event: '*', schema: 'public', table: 'orders' }, () => {
    reloadAdminOrders().catch((error) => showToast(error.message || 'تعذر تحديث سجل الطلبات.'));
  })
  .on('postgres_changes', { event: '*', schema: 'public', table: 'menu_categories' }, scheduleAdminMenuRefresh)
  ...
```
- نفس آلية الدفع اللحظي (`postgres_changes`)، `event: '*'` يعني تُغطى الثلاثة: إنشاء طلب جديد، تعديل حالته، وحذفه (إن وُجد).
- تُستدعى `reloadAdminOrders()` تلقائياً بمجرد أي حدث — تحديث سجل الطلبات بلوحة الإدارة فوري.
- نفس القناة تشترك أيضاً بتغييرات المنيو (أقسام/منتجات/خيارات) لتحديث عرض المنيو بالأدمن حياً — إضافة من الترحيل [`202609260013_menu_realtime_publication.sql`](../supabase/migrations/202609260013_menu_realtime_publication.sql) الذي يضيف هذه الجداول لنشر Realtime.

## 4. هل تتغير الحالة لحظياً؟ ✅ نعم من المطبخ إلى الأدمن — ⚠️ لا، من المطبخ إلى الويتر

### من المطبخ إلى الأدمن: نعم، لحظي ومؤكد
عندما يضغط المطبخ زر تغيير الحالة، يُنفَّذ [`kitchen-app.js:250`](../public/js/kitchen-app.js):
```js
const { data, error } = await supabase.rpc("update_kitchen_order_status", {...});
```
هذا `UPDATE` على جدول `orders` — وبما أن لوحة الإدارة مشتركة بنفس القناة على نفس الجدول بـ`event: '*'` (تشمل `UPDATE`)، **يصل تغيير الحالة للأدمن لحظياً تلقائياً**، بنفس آلية القسم 3، دون أي كود إضافي مطلوب.

### من المطبخ إلى الويتر: ⚠️ لا يوجد إطلاقاً — فجوة حقيقية
بحثت في `public/js/waiter-app.js` بالكامل: **لا يوجد أي اشتراك Realtime على جدول `orders`** (تحقق: `grep "table: 'orders'" waiter-app.js` → لا نتائج). موظف الويتر الذي أرسل الطلب **لا يملك أي طريقة لحظية ليعرف متى صار الطلب "جاهز للتسليم"** — لا جرس، لا إشعار، لا تحديث تلقائي لأي قائمة طلبات بجانبه. إن كانت هناك حاجة تشغيلية لأن يعرف الويتر لحظة جاهزية الطلب (مثلاً لتسليمه للسيارة)، **هذه الوظيفة غير موجودة حالياً بالكود إطلاقاً**، وليست مجرد عطل — هي ميزة لم تُبنَ.

## 5. جدول ملخص دقيق

| المسار | لحظي فعلاً؟ | الآلية | الحالة |
|---|---|---|---|
| زبون يطلب من `/menu` مباشرة | ❌ غير ممكن إطلاقاً بعد الآن | — | مُلغى عمداً؛ `place_customer_order` ممنوعة عن anon/authenticated من الخادم (تحقق حي) |
| ويتر يُنشئ طلباً ← يظهر بالمطبخ | ✅ نعم | Supabase Realtime، `postgres_changes` على `orders`، دفع WebSocket حقيقي | مؤكد من الكود، مع شبكة أمان لإعادة الاتصال |
| ويتر يُنشئ طلباً ← يظهر بالأدمن | ✅ نعم | نفس الآلية، قناة منفصلة بنفس الجدول | مؤكد من الكود |
| المطبخ يغيّر الحالة ← تنعكس بالأدمن | ✅ نعم | نفس قناة الأدمن تستقبل `UPDATE` تلقائياً | مؤكد من الكود |
| المطبخ يغيّر الحالة ← يعرف الويتر | ❌ لا يوجد | — | فجوة: لا اشتراك Realtime على `orders` في waiter-app.js إطلاقاً |
| منيو الزبون (أصناف/أسعار) يعدّله الأدمن ← ينعكس بشاشة الزبون/الويتر حياً | ✅ نعم (كلاهما) | كل من `menu-app.js` و`waiter-app.js` يشتركان بقناة Realtime على `menu_products`/`menu_categories`/خيارات المنتج | مؤكد من الكود |

**الجواب المباشر بجملة واحدة:** نعم، أي طلب حقيقي (من الويتر الآن، وليس من المنيو مباشرة) يظهر بالمطبخ والأدمن لحظياً وبنفس اللحظة تقريباً عبر Realtime حقيقي لا عبر تحديث دوري، وتغيير الحالة ينعكس لحظياً للأدمن أيضاً — **باستثناء واحد مهم:** الويتر نفسه لا يعرف لحظياً متى يصير طلبه جاهزاً، لأن هذا المسار تحديداً غير مبني بالكود إطلاقاً.
